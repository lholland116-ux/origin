======================================================================

This evidence documents the final production end-to-end validation of
Milestone 5 / M5G for the governed LVTChat CAPA AI workflow.

The validation demonstrates that:

1. A human can create and submit a CAPA intake.
2. Submission performs the controlled workflow transition from Draft
   Intake to Intake Submitted.
3. A governed AI intake advisory can be generated only against the
   submitted CAPA record.
4. The AI output remains advisory and proposed pending human review.
5. A human reviewer can explicitly ACCEPT, REJECT, or REVISE the AI
   advisory with no disposition preselected.
6. Human disposition of the AI advisory is not CAPA approval.
7. AI generation does not advance CAPA workflow or create a new
   controlled CAPA record version.
8. Human disposition of the AI advisory does not advance CAPA workflow
   or create a new controlled CAPA record version.
9. Existing CAPA records can be reopened after navigation, reload, or
   reauthentication using an authoritative tenant-scoped retrieval.

4. EXISTING-CASE REOPENING DEFECT AND CORRECTION
======================================================================

During final production validation, CAPA-000008 could be listed after
reauthentication but could not be reopened.

The CAPA workspace rows were display-only. The detailed CAPA view and
AI Intake Analysis controls required the client-side createdCapa state,
which was populated only when a CAPA had been created during the active
component lifecycle.

The defect therefore prevented an existing submitted CAPA from being
rehydrated after navigation, reload, logout, or login.

Correction:

An explicit "Open case" action was added to each CAPA workspace row.

The action:

- performs an authorized GET /api/capa?id=<case-id>;
- relies on the existing tenant-scoped server retrieval;
- validates that the returned CAPA identity matches the selected case;
- validates the authoritative current record and intake section;
- reconstructs the controlled client-side CAPA summary only after
  successful validation;
- fails closed for incomplete or mismatched server responses;
- clears prior AI advisory and human-review state before changing
  cases;
- does not weaken CAPA authorization;
- does not trust the lightweight workspace-list representation as the
  authoritative controlled record.

5. AUTHENTICATION INCIDENT DURING VALIDATION
======================================================================

During the final validation sequence, Google OAuth successfully returned
to:

/auth/callback

but the callback request encountered a Vercel
MIDDLEWARE_INVOCATION_TIMEOUT.

The routing middleware was performing a remote Supabase auth.getUser()
call for /auth/callback before the callback route could exchange the
OAuth authorization code.

Correction:

/auth/callback was excluded from the middleware matcher while normal
Supabase session-refresh behavior remained enabled for the rest of the
application.

Implementation commit:
15db0b0 Bypass auth callback in Supabase middleware

Production verification confirmed successful Google authentication and
normal navigation to the authenticated LVTChat interface.

The middleware-to-proxy migration was intentionally not combined with
this incident correction.
